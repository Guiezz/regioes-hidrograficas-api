# CI/CD da API (GitHub Actions) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** CI em todo PR da API, deploy no Render disparado pelo Actions após merge no `main` (só com CI verde), e um botão manual para rodar o seeder no Neon.

**Architecture:** Dois workflows. `ci-cd.yml` tem os jobs `test` e `docker` (sempre) e `deploy` (só em push no `main`, depois dos dois). A lógica de deploy fica num script bash testável localmente contra um mock da API do Render. `seed.yml` é só `workflow_dispatch`, com confirmação digitada.

**Tech Stack:** GitHub Actions, Go 1.25, Docker, bash + curl + jq, API REST do Render (`https://api.render.com/v1`), psql.

**Spec:** `/Users/guilhermebessa/Projetos/sadgrh/regioes-hidrograficas-web/docs/superpowers/specs/2026-10-18-ci-cd-github-actions-design.md` (seções "API", "Proteção de branch", "Riscos"). Leia antes de começar.

## Review Focus

1. **Deploy do Render falha (build_failed etc.)** → o job falha com o status na mensagem, não fica esperando até o timeout. *Teste: Task 2, Step 2 (cenário `build_failed`).*
2. **Resposta da API do Render sem `id`/`status` (formato inesperado ou 401)** → falha na hora com o corpo cru no log, sem a chave. *Teste: Task 2, Step 2 (cenário `401`).*
3. **Render hibernando** → teste de fumaça tenta de novo por até 5 min antes de falhar. *Teste: Task 2, Step 2 (cenário fumaça 503 → 200).*
4. **Alguém dispara o seed sem digitar `SEED` exato** (ex.: `seed`, vazio) → falha antes de qualquer acesso ao banco. *Teste: Task 3, Step 2.*
5. **Seeder termina com código 0 mas registrou `❌`** → o job falha. *Teste: Task 3, Step 2.*

### Task 2: Deploy no Render

**Files:**
- Create: `.github/scripts/render-deploy.sh` (executável)
- Create: `.github/scripts/render-deploy.test.sh` (executável; mock + cenários)
- Modify: `.github/workflows/ci-cd.yml` (job `deploy`)

**Interfaces:**
- `render-deploy.sh` lê do ambiente: `RENDER_API_KEY`, `RENDER_SERVICE_ID`, `COMMIT_SHA`, `SMOKE_URL` (obrigatórios) e `RENDER_API_BASE` (padrão `https://api.render.com/v1`), `POLL_INTERVAL` (padrão `15`), `DEPLOY_TIMEOUT` (padrão `1200`), `SMOKE_TIMEOUT` (padrão `300`). Exit 0 = deploy `live` + fumaça ok; exit 1 = qualquer falha. Se `GITHUB_STEP_SUMMARY` existir, acrescenta um resumo em markdown (commit, id do deploy, status final, resultado da fumaça).

- [x] **Step 1: Escrever o teste primeiro** (`render-deploy.test.sh`)
  Sobe um mock HTTP com `python3` (porta livre, em background, morto no `trap EXIT`) que imita:
  `POST /services/<id>/deploys` → `201 {"id":"dep-test","status":"created"}`; `GET /services/<id>/deploys/dep-test` → sequência de status configurável por cenário; `GET /smoke` → sequência de códigos configurável.
  Roda o script com `POLL_INTERVAL=0`, `RENDER_API_BASE=http://127.0.0.1:<porta>`, `SMOKE_URL=http://127.0.0.1:<porta>/smoke` e timeouts curtos. Cenários e expectativas:
  - `ok`: status `build_in_progress → update_in_progress → live`, fumaça `200` com corpo `[{"id":1}]` → exit 0.
  - `build_failed`: status `build_in_progress → build_failed` → exit 1 e stderr contém `build_failed`.
  - `401`: POST responde `401 {"message":"unauthorized"}` → exit 1, stderr contém `401` e **não** contém o valor de `RENDER_API_KEY` usado no teste.
  - `fumaca_lenta`: `live`, fumaça `503, 503, 200` → exit 0.
  - `fumaca_vazia`: `live`, fumaça `200` com corpo `[]` → exit 1.
  - `timeout`: status sempre `build_in_progress`, `DEPLOY_TIMEOUT=1` → exit 1 e stderr contém `timeout`.
  Imprime `PASS <cenário>`/`FAIL <cenário>` e sai com 1 se algum falhar.

- [x] **Step 2: Rodar e ver falhar**
  Run: `.github/scripts/render-deploy.test.sh`
  Expected: FAIL (script ainda não existe).

- [x] **Step 3: Implementar `render-deploy.sh`**
  `set -euo pipefail`; valida variáveis obrigatórias; `curl -sS` com `Authorization: Bearer` e `Accept: application/json`; POST com corpo `{"commitId":"$COMMIT_SHA"}`; extrai `id` com `jq -er` (falha mostrando código HTTP e corpo se faltar); poll até `live` (sucesso) ou `build_failed|update_failed|canceled|deactivated|pre_deploy_failed` (falha) ou timeout; depois fumaça: código 200 **e** `jq -e 'type=="array" and length>0'`, tentando a cada 10 s (ou `POLL_INTERVAL` se menor) até `SMOKE_TIMEOUT`. Mensagens em português no stderr.

- [x] **Step 4: Rodar e ver passar**
  Run: `.github/scripts/render-deploy.test.sh`
  Expected: `PASS` nos 6 cenários, exit 0.

- [x] **Step 5: Job `deploy` no workflow**

### Task 3: Seed manual no Neon

**Files:**
- Create: `.github/scripts/seed-guard.sh` (executável)
- Create: `.github/scripts/seed-guard.test.sh` (executável)
- Create: `.github/workflows/seed.yml`

**Interfaces:**
- `seed-guard.sh confirm <valor>` → exit 0 só se `<valor>` for exatamente `SEED`; senão exit 1 com mensagem `Confirmação inválida: digite SEED para rodar o seed.`
- `seed-guard.sh check-log <arquivo>` → exit 1 se o arquivo contiver `❌` (mostra as linhas com `❌`), exit 0 caso contrário.

- [x] **Step 1: Teste primeiro** (`seed-guard.test.sh`)
  Casos: `confirm SEED` → 0; `confirm seed` → 1; `confirm ""` → 1; `confirm " SEED"` → 1; `check-log` em arquivo com `🌊 PROCESSANDO BACIA` e `🚀 SEED COMPLETO` → 0; em arquivo com uma linha `❌ Erro ao criar bacia X` → 1 e a linha aparece na saída. Imprime `PASS`/`FAIL` por caso; exit 1 se algum falhar.

- [x] **Step 2: Rodar e ver falhar; implementar `seed-guard.sh`; rodar e ver passar**
  Run: `.github/scripts/seed-guard.test.sh`
  Expected: primeiro FAIL; depois da implementação, `PASS` em todos os 6 casos.

- [x] **Step 3: Escrever `seed.yml`**
  `name: Seed (produção)`; só `workflow_dispatch` com input `confirmacao` (`required: true`, `type: string`, descrição `Digite SEED para APAGAR e recriar todas as tabelas do banco de produção`). Job `seed` com `name: Seed do banco de produção (Neon)`, `environment: production`, `concurrency: { group: seed-production, cancel-in-progress: false }`, `timeout-minutes: 30`. Passos:
  1. `seed-guard.sh confirm "$CONFIRMACAO"` — o input passado via `env:`, nunca interpolado direto no script.
  2. checkout → setup-go.
  3. `go run ./cmd/seeder 2>&1 | tee seed.log` com `DATABASE_URL: ${{ secrets.NEON_DATABASE_URL }}` em `env:` e `set -o pipefail`.
  4. `seed-guard.sh check-log seed.log`.
  5. `if: always()` depois do seeder: instalar `postgresql-client` se `psql` não existir; contar linhas de cada tabela de `public` (via `\gexec` sobre `information_schema.tables`) e escrever uma tabela markdown `| Tabela | Linhas |` no `GITHUB_STEP_SUMMARY`.
